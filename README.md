# TypeKnight - Neon Cyber-Cat

A cyberpunk arcade game for learning TypeScript's type system. A cyber-cat hacker jacks into
corporate servers and patches broken `any` code into strict, working types - using all 190
challenges from [type-challenges](https://github.com/type-challenges/type-challenges).

## Stack

- Next.js (App Router) + TypeScript + Tailwind CSS v4
- [`@monaco-editor/react`](https://github.com/suren-atoyan/monaco-react) - the VS Code editor in
  the browser, for editing and inline squiggles
- The `typescript` package itself, run directly in the browser (`lib/type-checker.ts`), for the
  actual pass/fail check - see "Why not Monaco's worker?" below
- [`marked`](https://github.com/markedjs/marked) + [`highlight.js`](https://github.com/highlightjs/highlight.js)
  for rendering challenge descriptions with syntax-highlighted code blocks
- [Playwright](https://playwright.dev) for e2e tests, run in CI on every push/PR

## How it works

- `lib/generated-challenges.json` is a static snapshot of the official type-challenges repo
  (template, tests, description, tags, difficulty) for all 190 challenges, produced by a one-off
  script against a shallow clone of `type-challenges/type-challenges` (real templates and tests,
  not hand-written).
- `lib/challenges.ts` loads that dataset and exposes helpers (`getChallenge`, `challengesByLevel`,
  `editorSource`, `solutionsUrl`).
- `lib/type-utils.ts` mirrors `@type-challenges/utils` (`Equal`, `Expect`, `NotEqual`, `Alike`,
  etc.).
- `lib/ts-libs.json` bundles the subset of TypeScript's `lib.*.d.ts` files needed for an ESNext,
  no-DOM program (generated by `scripts/generate-ts-libs.mjs`).
- `lib/type-checker.ts` runs `ts.createProgram` against an in-memory `CompilerHost` fed by the two
  files above, entirely in the browser, no worker or network round-trip. `checkTypeScript(source)`
  returns real diagnostics synchronously. Parsed lib files are cached across calls so repeat checks
  are fast.
- `components/QuestEditor.tsx` combines a challenge's template + test cases into one editable file.
  Hitting **Run Exploit** runs `checkTypeScript` on the current editor contents - zero diagnostics
  means the patch is correct. `// @ts-expect-error` cases in the official tests work out of the
  box, since TS itself flags an unused directive when the expected error doesn't occur.
- Progress and credits are stored in `localStorage` (`lib/progress.ts`) - no backend.

### Why not Monaco's worker?

The first version of the checker used Monaco's own `getTypeScriptWorker()` /
`getSemanticDiagnostics()` (and later its internal diagnostics/marker adapter). Both turned out to
be unreliable in this app's setup: a manually-acquired worker client would throw
`Could not find source file` indefinitely once a model's content was set via a direct API call
(not just typed), and Monaco's diagnostics adapter never ran its first validation pass at all for
a model that was never edited - even after 20+ seconds idle. Running the actual TypeScript
compiler ourselves sidesteps both bugs and is deterministic, which the e2e suite depends on.

## Development

```bash
npm install
npm run dev
```

Then open [http://localhost:3000](http://localhost:3000).

```bash
npm run format        # prettier --write
npm run format:check  # prettier --check
npm run lint          # eslint
npm run build         # production build
npm run test:e2e      # playwright test (starts its own dev server)
```

## e2e tests

`e2e/exploit.spec.ts` covers the actual Run Exploit flow: the dungeon map linking into a quest, a
failing check on the unmodified stub, and a passing check on a corrected solution. Runs on every
push/PR via `.github/workflows/e2e.yml`. Locally:

```bash
npx playwright install chromium   # once
npm run test:e2e
```

## Solution walkthroughs

The "Backchannel" panel offers tiered hints per challenge: an approach explanation, then the actual
solution code, sourced from [`ghaiklor/type-challenges-solutions`](https://github.com/ghaiklor/type-challenges-solutions)
(CC-BY-4.0, attributed in the UI). `lib/generated-solutions.json` is checked in and only includes
walkthroughs that were verified to actually pass `checkTypeScript` against the real test cases -
around 50 challenges have a real solution logged; the rest fall back to just the docs link and the
GitHub search link. To regenerate:

```bash
git clone --depth 1 https://github.com/ghaiklor/type-challenges-solutions.git /tmp/tcs
node scripts/generate-solutions.mjs /tmp/tcs
```

Then re-run the pass/fail filter (combines each `solutionCode` with the challenge's real
`testCases` and keeps only the ones with zero diagnostics) before committing the result.

## Regenerating the challenge dataset

`lib/generated-challenges.json` is checked in, not fetched at runtime. To refresh it against a
newer type-challenges commit:

```bash
git clone --depth 1 https://github.com/type-challenges/type-challenges.git /tmp/type-challenges
node scripts/generate-challenges.mjs /tmp/type-challenges
```

`lib/ts-libs.json` only needs regenerating after a TypeScript version bump:

```bash
node scripts/generate-ts-libs.mjs
```
